# video-and-push

Review: 63 claims confirmed, 10 corrected, 0 could not be verified.

## Summary

Browser video is fully feasible with go2rtc (MIT, v1.9.14 released 2026-01-19): a single static binary (go2rtc_win64.zip for Windows, bare go2rtc_linux_arm64 for a Pi) that reads a go2rtc.yaml with a `streams:` map of name -> source URL(s), accepts sources as rtsp://, onvif://, tapo://, dvrip://, isapi:// (Hikvision backchannel only, paired with RTSP), http:// (JPEG snapshot, multipart MJPEG, HLS, FLV), ffmpeg:, exec:, webrtc:, homekit:// and more, and exposes them at :1984 as WebRTC (POST /api/webrtc?src= WHEP with application/sdp, or the JSON WebSocket /api/ws?src= used by its own player), MSE fMP4 over that same WebSocket, progressive MP4 (/api/stream.mp4), HLS (/api/stream.m3u8), MJPEG (/api/stream.mjpeg, multipart/x-mixed-replace) and JPEG snapshots (/api/frame.jpeg); streams can be added, patched and removed at runtime with PUT/PATCH/DELETE /api/streams (persisted into the yaml), and there is no Dahua-specific scheme, Dahua is plain rtsp:///cam/realmonitor plus http snapshot.cgi. The shipped `www/video-rtc.js` (class VideoRTC extends HTMLElement, ES module) plus `video-stream.js` (customElements.define('video-stream')) give a drop-in `<video-stream src="/api/ws?src=cam1" mode="webrtc,mse,hls,mjpeg">` element that auto-negotiates WebRTC -> MSE -> HLS -> MJPEG; the hub should reverse-proxy go2rtc (HTTP and WebSocket) under its own HTTPS origin because go2rtc has only Basic auth, skips auth for localhost, and only supports `origin: "*"` for CORS. FFmpeg is not bundled in the binary and is optional, but it becomes required for JPEG/MJPEG output from H.264-only cameras (`ffmpeg:cam1#video=mjpeg`) and for any transcoding; the Docker image ships FFmpeg. Push notifications are feasible with the `web-push` npm package (3.6.7, MPL-2.0, Node >=16): generate VAPID keys once, `setVapidDetails('mailto:...')`, `sendNotification(subscription, payload, {TTL, urgency, topic})`; the browser subscribes with `pushManager.subscribe({userVisibleOnly:true, applicationServerKey})` and the service worker handles `push` (must call showNotification inside waitUntil) and `notificationclick` (focus/openWindow). Android Chrome delivers via fcm.googleapis.com even with the browser closed; iOS/iPadOS needs 16.4+, the PWA added to the Home Screen with a manifest `display: standalone`/`fullscreen`, permission requested from a user tap, every push must show a notification or Safari revokes the subscription, subject must not be a localhost mailto, and payloads are capped at 4 KB. The hub therefore needs a real HTTPS origin (trusted certificate) for both the service worker and push, and outbound internet (fine over the SIM path) to reach FCM/Apple push servers. vite-plugin-pwa 1.3.0 (MIT) with `strategies: 'injectManifest', srcDir: 'src', filename: 'sw.ts'` lets one custom service worker hold both precaching (`precacheAndRoute(self.__WB_MANIFEST)`) and the push handlers, registered via `registerSW` from 'virtual:pwa-register'. Without go2rtc, a `<img>` pointed at a camera's own multipart MJPEG URL (Hikvision /ISAPI/Streaming/channels/102/httpPreview with the sub-stream set to MJPEG, Dahua /cgi-bin/mjpg/video.cgi?channel=1&subtype=1) or JPEG snapshot polling (/ISAPI/Streaming/channels/101/picture, /cgi-bin/snapshot.cgi?channel=1, both Digest auth) works in Chrome/Safari/Firefox, and static FFmpeg builds are available for win64 and linuxarm64 in GPL and LGPL variants (BtbN) or GPLv3 only (gyan.dev, johnvansickle).

## Corrections from review (these override anything below)

- **Claim:** FACT: /api/streams handler semantics: PUT creates, PATCH updates by name, DELETE by src=name, POST src->dst, ALL persisted via app.PatchConfig into the yaml; GET with src returns that stream
  **Correction:** Only PUT and DELETE call app.PatchConfig. PATCH calls streams.Patch(name, src) and is IN-MEMORY ONLY (lost on go2rtc restart); it takes a single src (query.Get), not a list, and if src equals an existing stream name or an rtsp://.../<existing name> URL it ALIASES name to that stream instead of setting a source. POST (play/publish) is not persisted either. GET ?src= uses streams.Get(src): unknown name -> HTTP 404 with empty body (it never creates a stream); adding video=/audio= query params makes it a live probe. PUT: if PatchConfig fails (e.g. config given only inline, ConfigPath empty -> 'config file disabled') the stream still exists in memory but the response is 400. DELETE never 404s (delete on missing key is a no-op). Sources given through the API are run through streams.Validate: schemes exec/echo/expr are rejected ('source from insecure producer') and any source containing whitespace is rejected ('source with spaces may be insecure').
  Source: https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/streams/api.go ; https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/streams/streams.go ; https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/streams/handlers.go ; internal/app/config.go
- **Claim:** FACT: Consumer endpoints accept src as either a stream name or a raw source URL (ad-hoc stream, optional name= to persist under a name)
  **Correction:** Only handlers that call streams.GetOrPatch accept a raw URL: GET /api/frame.jpeg, GET /api/stream.mp4, and the WebSocket message handlers (webrtc, webrtc/offer, mse, mp4, hls, mjpeg). These use streams.Get (existing NAME only, else 404 'stream not found'): POST /api/webrtc?src= (WHEP), GET /api/frame.mp4, GET /api/stream.m3u8, GET /api/stream.mjpeg, GET /api/stream.y4m, GET /api/streams?src=, and the RTSP server. name= with GetOrPatch calls Patch() which is in-memory only: nothing is written to go2rtc.yaml, so 'persist' is wrong. Raw URLs are subject to streams.Validate (no exec/echo/expr, no whitespace).
  Source: https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/streams/streams.go ; internal/webrtc/server.go ; internal/mp4/mp4.go ; internal/hls/hls.go ; internal/mjpeg/mjpeg.go ; internal/mp4/ws.go ; internal/hls/ws.go
- **Claim:** FACT: WebSocket API /api/ws?src=<name> exchanges JSON {type,value}; types webrtc/offer, webrtc/answer, webrtc/candidate, mse, hls, mjpeg, v2 'webrtc', 'error'; WS origin check: same host (port ignored) unless origin '*'
  **Correction:** Message protocol is correct as stated. The origin detail is wrong: with api.origin unset, CheckOrigin allows (a) no Origin header, (b) Origin host == request Host header exactly, or (c) Origin host WITH ITS PORT STRIPPED == the full request Host header. The port is stripped only from the Origin, never from Host, so a page on http://hub:5173 or https://hub:8443 opening ws://hub:1984/api/ws is REJECTED (Host is 'hub:1984'). It only passes when the Host header carries no port (go2rtc behind a proxy on 80/443) or when the proxy rewrites Host/drops Origin. Also: error frames are {"type":"error","value":"<msgType>: <text>"}; the 'mp4' request is answered with a frame of type 'mse' (handlerWSMP4 writes Type:"mse"); ?dst=<name> is also accepted on /api/ws for WebRTC ingest.
  Source: https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/api/ws/ws.go (initWS) ; internal/api/ws/README.md ; internal/webrtc/webrtc.go ; internal/mp4/ws.go
- **Claim:** FACT: MJPEG/JPEG endpoints require the stream to contain an MJPEG codec; H.264 cameras need an ffmpeg transcode source for /api/frame.jpeg and /api/stream.mjpeg
  **Correction:** True only for /api/stream.mjpeg (and WS 'mjpeg'). /api/frame.jpeg does NOT need an MJPEG source: handlerKeyframe grabs one keyframe with magic.NewKeyframe and, when the codec is H264 or H265, pipes it through the local ffmpeg binary itself (ffmpeg.JPEGWithQuery: 'ffmpeg -hide_banner -i - -c:v mjpeg -f mjpeg -', plus scale/transpose from width|w, height|h, rotate, hardware|hw). The built-in mjpeg encoder is used, so an LGPL ffmpeg build is sufficient. A separate 'ffmpeg:cam#video=mjpeg' source is only needed for continuous MJPEG.
  Source: https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/mjpeg/mjpeg.go ; https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/ffmpeg/jpeg.go ; internal/ffmpeg/version.go

- **Claim:** ENDPOINT: go2rtc WebSocket signalling + MSE/HLS/MJPEG transport — ws://host:1984/api/ws?src={name}; Origin must match host (port ignored) unless api.origin '*'
  **Correction:** Message formats are right.   **Correction:** They are properties only, not attributes (no observedAttributes in VideoRTC). Use: import './video-stream.js'; const el = document.createElement('video-stream'); el.mode = 'webrtc,mse,hls,mjpeg'; el.media = 'video,audio'; el.background = false; el.pcConfig.iceServers = [...]; el.src = '/api/ws?src=' + encodeURIComponent(name); parent.appendChild(el). - **Claim:** ENDPOINT: Web Push hub sends notification (web-push) — payload string/Buffer <= 4096 bytes; options TTL, urgency, topic, contentEncoding, headers, timeout, proxy/agent
  **Correction:** The call shape and options are correct, but the size limit is wrong: 4096 bytes is the guaranteed size of the ENCRYPTED request body. With aes128gcm (web-push default) that leaves at most 3993 bytes of plaintext payload (86-byte header + 1 padding byte + 16-byte AEAD tag); Apple separately caps at 4 KB. Keep the JSON payload well under ~3.9 KB (send ids/urls, not images).

## Added by review (things an implementer needs)

- **go2rtc PATCH /api/streams and GetOrPatch are not persisted; only PUT/DELETE write go2rtc.yaml** For the 're-point camera to another network/IP' flow the hub must use PUT /api/streams?name=<name>&src=<url>[&src=<url2>] (overwrites the stream in memory AND writes streams.<name> into the yaml) rather than PATCH. PUT needs a real config file path (go2rtc started with a file, not only inline -c '{...}'), otherwise PatchConfig returns 'config file disabled' -> HTTP 400 while the in-memory stream is still created. PUT/PATCH return an empty 200 body on success, 400 with a text error otherwise. (https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/streams/api.go ; https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/app/config.go)
- **API-supplied sources are validated: no exec/echo/expr, no whitespace** streams.Validate rejects any source whose scheme is marked insecure (exec, echo, expr call streams.MarkInsecure) and any source matching \s. So via PUT/PATCH/POST/GetOrPatch you cannot add 'exec:...' or an ffmpeg source with spaces (e.g. '#raw=-r 10'); such sources must be written into go2rtc.yaml by the hub before starting go2rtc. 'ffmpeg:cam#video=mjpeg' (no spaces) is accepted. Never pass a user-controlled string as src to the GetOrPatch endpoints. (https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/streams/handlers.go ; internal/exec/exec.go ; internal/echo/echo.go ; internal/expr/expr.go)

Sending also requires the hub to have outbound internet to fcm.googleapis.com / *.push.apple.com / the browser's push service, so 'action complete' pushes cannot be delivered while the hub's uplink is down. The microphone for two-way audio is likewise HTTPS-only. (https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers ; https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers ; https://raw.githubusercontent.com/AlexxIT/go2rtc/master/README.md)
- **Web Push response handling the hub must implement** Success is 201 Created. TTL header is mandatory in the protocol (400 if omitted); web-push defaults TTL to 2419200 s (4 weeks), so pass a short TTL (e.g. 60-300 s) for 'gate opened' style messages, and TTL 0 means deliver-now-or-drop. On 404 or 410 from the push service delete the stored subscription (expired/unsubscribed; Apple: 410 'device token has expired', 404 invalid token). Apple also returns 403 BadJwtToken for a localhost/invalid VAPID subject, 413 PayloadTooLarge, 429 TooManyRequests. web-push rejects with a WebPushError carrying statusCode, headers, body, endpoint. Use topic to collapse repeated notifications for the same device (<= 32 base64url chars) and urgency 'high' for immediate delivery. (https://www.rfc-editor.org/rfc/rfc8030.html (5, 5.2, 7.3) ; https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers ; https://raw.githubusercontent.com/web-push-libs/web-push/master/src/web-push-lib.js (DEFAULT_TTL = 2419200) ; https://raw.githubusercontent.com/web-push-libs/web-push/master/README.md)
- **web-push packaging and VAPID specifics** Published web-push 3.6.7 is CommonJS (main src/index.js, require('web-push')); the GitHub master branch has since been rewritten as ESM (import https from 'node:https') and is not what npm installs, so do not copy code from master. TypeScript types come from @types/web-push (3.6.4). Library validation: subject must be https: or mailto: (warns on localhost), public key must decode to 65 bytes, private key to 32 bytes; JWT expiry defaults to 12 h, max 24 h; only options headers, gcmAPIKey, vapidDetails, TTL, contentEncoding, urgency, topic, proxy, agent, timeout are accepted (any other key throws). Apple's doc says not to refresh the VAPID JWT more than once per hour, while web-push signs a new JWT on every sendNotification call. (https://registry.npmjs.org/web-push/latest ; https://registry.npmjs.org/@types/web-push/latest ; https://raw.githubusercontent.com/web-push-libs/web-push/master/src/web-push-lib.js ; https://raw.githubusercontent.com/web-push-libs/web-push/master/src/vapid-helper.js ; https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)
- **Browser-side push details omitted** applicationServerKey may be passed directly as the base64url string from generateVAPIDKeys or as an ArrayBuffer/Uint8Array; Chrome and Edge reject the promise unless userVisibleOnly is true; subscribe() should be called from a user gesture (Firefox 72+ enforces, iOS requires it). Subscriptions can be invalidated by the push service: handle the service worker 'pushsubscriptionchange' event and re-POST the new subscription, and re-check registration.pushManager.getSubscription() on app start. In the MDN notificationclick sample the test client.url === '/' never matches an absolute URL; compare new URL(client.url).pathname or just focus the first window client. On iOS each Home Screen install has its own subscription. (https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe ; https://developer.mozilla.org/en-US/docs/Web/API/Push_API ; https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/notificationclick_event ; https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- **vite-plugin-pwa injectManifest extras** workbox-precaching must be added as a dev dependency for the custom SW; srcDir is relative to project root and filename relative to srcDir; the service worker is not active under 'vite dev' unless devOptions is enabled, so push must be tested against a production build (or devOptions.enabled with type 'module'). onRegisteredSW(swUrl, registration) is the hook that hands you the ServiceWorkerRegistration for pushManager.subscribe; alternatively await navigator.serviceWorker.ready. (https://vite-pwa-org.netlify.app/guide/inject-manifest.html ; https://vite-pwa-org.netlify.app/frameworks/)
- **Hikvision ISAPI PTZ and capability details (vendor document)** PUT /ISAPI/PTZCtrl/channels/<ch>/continuous with body <PTZData version="2.0" xmlns="http://www.isapi.org/ver20/XMLSchema"><pan>xx</pan><tilt>yy</tilt><zoom>zz</zoom></PTZData>: pan >0 right / <0 left, tilt >0 up / <0 down, zoom >0 in / <0 out, range -100..100, 0 = stop (a stop request with all zeros must be sent). Check support first with GET /ISAPI/PTZCtrl/channels (PTZChannelList with <id>, panSupport/tiltSupport/zoomSupport; empty list = no PTZ). Presets: PUT /ISAPI/PTZCtrl/channels/1/presets/<id> (set), PUT .../presets/<id>/goto (call), GET .../presets (list). Home: PUT .../homeposition and .../homeposition/goto. Responses are <ResponseStatus> with statusCode 1 / statusString OK. Device info: GET /ISAPI/System/deviceInfo. Content-Type text/xml or application/xml. Stream channel id = channel*100 + stream (101 main, 102 sub). (http://www.hikvisioneurope.com/za/portal/portal/02-Technical%20Materials/03-How%20to%20document/02-Product%20Trouble%20Shooting/08-Third-party%20Integration/How%20to%20integrate%20Hikvision%20PTZ%20function.pdf ; https://raw.githubusercontent.com/AlexxIT/go2rtc/master/internal/isapi/README.md)
- **Hikvision MJPEG-over-HTTP limitations** httpPreview works only on the sub-stream (channel x02) after setting Video Encoding to MJPEG, firmware V4.1+, and the vendor note says DS-2CD1X23G0 series cameras do not support it. The vendor snapshot example is /ISAPI/Streaming/channels/1/picture (channel 1) while integrations use /101/picture; try 101 then 1. Switching the sub-stream to MJPEG removes the H.264 sub-stream that the hub would otherwise use for low-bitrate SIM-path viewing. (https://www.hikvision.com/content/dam/hikvision/en/support/how-to/how-to-document/network-cameras/How-to-Get-IPC-MJPEG-Stream-via-HTTP-Commands.pdf)
- **Dahua CGI details needed for an adapter** PTZ: GET /cgi-bin/ptz.cgi?action=start&channel=<n>&code=<Code>&arg1=0&arg2=<speed 1-8>&arg3=0 starts continuous motion that runs until the matching action=stop with the same code (always send stop in a finally). Codes: Up, Down, Left, Right, LeftUp, RightUp, LeftDown, RightDown, ZoomTele, ZoomWide; preset recall: code=GotoPreset&arg1=0&arg2=<preset>&arg3=0; list presets: /cgi-bin/ptz.cgi?action=getPresets&channel=<n>; status: action=getStatus. Events: /cgi-bin/eventManager.cgi?action=attach&codes=[All]&heartbeat=<1..60> returns a long-lived multipart text stream with lines like 'Code=VideoMotion;action=Start;index=0' and periodic 'Heartbeat'. snapshot.cgi channel is 1-based on most firmware. Device info: /cgi-bin/magicBox.cgi?action=getSystemInfo|getDeviceType|getSoftwareVersion; reboot: magicBox.cgi?action=reboot. RTSP: rtsp://user:pass@host:554/cam/realmonitor?channel=1&subtype=0|1. (https://raw.githubusercontent.com/rroller/dahua/main/custom_components/dahua/client.py ; https://raw.githubusercontent.com/rroller/dahua/main/custom_components/dahua/camera.py ; https://raw.githubusercontent.com/tchellomello/python-amcrest/master/src/amcrest/ptz.py)
- **FFmpeg build choice for Raspberry Pi and Windows** johnvansickle static builds are stale (release 7.0.2, git 2024-06-29) and GPLv3; gyan.dev builds are GPLv3 and include libx264 even in 'essentials'; BtbN publishes daily gpl/lgpl builds for win64, winarm64, linux64, linuxarm64 (glibc >= 2.28) with checksums.sha256 and keeps the last build of each month for two years, which is the pinnable option. If the hub only needs snapshots/MJPEG (built-in mjpeg encoder) and audio transcoding, an LGPL build suffices and avoids GPL redistribution obligations; the hub should download rather than bundle ffmpeg, or ship the GPL/LGPL notices and source offer. (https://johnvansickle.com/ffmpeg/ ; https://www.gyan.dev/ffmpeg/builds/ ; https://raw.githubusercontent.com/BtbN/FFmpeg-Builds/master/README.md ; https://ffmpeg.org/legal.html)

## Calls

### go2rtc: list all streams

```
http GET http://127.0.0.1:1984/api/streams
```
- Params: none
- Auth: Basic (api.username/password); localhost bypasses auth unless local_auth: true
- Response: application/json object keyed by stream name with producers[] and consumers[]
- Notes: Use to verify a camera is online (producers non-empty while consumed).
- Source: https://github.com/AlexxIT/go2rtc/blob/master/website/api/openapi.yaml

### go2rtc: get one stream info / probe

```
http GET http://127.0.0.1:1984/api/streams?src={name}
```
- Params: src=stream name (or a raw source URL, which creates an ad-hoc stream; add name= to persist it)
- Auth: Basic
- Response: application/json {producers:[...], consumers:[...]}; 404 if unknown
- Notes: Adding video/audio query params makes it probe codecs.
- Source: https://github.com/AlexxIT/go2rtc/blob/master/internal/streams/api.go

### go2rtc: add (create) stream

```
http PUT http://127.0.0.1:1984/api/streams?name={name}&src={urlencoded source}&src={second source optional}
```
- Params: src (required, repeatable = multiple sources), name (optional, defaults to src)
- Auth: Basic
- Response: 200 empty on success; 400 with error text
- Notes: Persists into go2rtc.yaml via app.PatchConfig(['streams', name], src[]). Example sources: rtsp://user:pass@ip/cam/realmonitor?channel=1&subtype=0, tapo://cloudpass@ip, onvif://user:pass@ip, dvrip://user:pass@ip:34567?channel=0&subtype=0, http://user:pass@ip/cgi-bin/snapshot.cgi?channel=1, ffmpeg:{name}#video=mjpeg
- Source: https://github.com/AlexxIT/go2rtc/blob/master/internal/streams/api.go

### go2rtc: update stream source

```
http PATCH http://127.0.0.1:1984/api/streams?name={name}&src={urlencoded source}
```
- Params: name (required), src (required)
- Auth: Basic
- Response: 200 empty; 400 on error
- Notes: Use when re-pointing a camera to a new IP after a WiFi/SIM switch.
- Source: https://github.com/AlexxIT/go2rtc/blob/master/internal/streams/api.go

### go2rtc: delete stream

```
http DELETE http://127.0.0.1:1984/api/streams?src={name}
```
- Params: src = stream NAME (not URL)
- Auth: Basic
- Response: 200 empty; removes key from yaml
- Source: https://github.com/AlexxIT/go2rtc/blob/master/internal/streams/api.go

### go2rtc: play audio to camera speaker (two-way audio) / publish stream

```
http POST http://127.0.0.1:1984/api/streams?dst={cameraName}&src=ffmpeg:http://example.com/song.mp3#audio=pcma#input=file
```
- Params: dst = existing stream with backchannel; src = source URL (ffmpeg:… for transcoding); empty src stops playback. Reverse (src=camera&dst=rtmps://…) publishes to RTMP
- Auth: Basic
- Response: application/json stream object; 400/404/500 with text
- Notes: Tapo supports only PCMA/8000; some Dahua support PCMA/48000.
- Source: https://github.com/AlexxIT/go2rtc/blob/master/internal/streams/README.md

### go2rtc: read / rewrite / merge config

```
http GET|POST|PATCH http://127.0.0.1:1984/api/config
```
- Params: body = YAML text (POST rewrites whole file, PATCH merges)
- Auth: Basic
- Response: GET: application/yaml; 404 if no config file
- Notes: Also /api/restart, /api/exit, /api/log, /api/schemes (supported source schemes), /api/onvif (discovery), /api/ffmpeg/devices, /api/ffmpeg/hardware.
- Source: https://github.com/AlexxIT/go2rtc/blob/master/website/api/openapi.yaml

### go2rtc: WebRTC WHEP (sync SDP exchange)

```
http POST http://127.0.0.1:1984/api/webrtc?src={name}
```
- Params: Body: SDP offer. Content-Type: application/sdp (WHEP, response 201 application/sdp) | application/json {"type":"offer","sdp":"v=0…"} (response 200 application/json {"type":"answer","sdp":…}) | anything (raw SDP, 200)
- Auth: Basic
- Response: SDP answer with complete ICE candidates
- Notes: Media flows P2P over port 8555 TCP/UDP (webrtc.listen), NOT through the HTTP proxy; set webrtc.candidates for the hub's LAN/public IP. ?dst= variant is WHIP ingest.
- Source: https://github.com/AlexxIT/go2rtc/blob/master/website/api/openapi.yaml

### go2rtc: WebSocket signalling + MSE/HLS/MJPEG transport (what video-rtc.js uses)

```
http GET (Upgrade: websocket) ws://127.0.0.1:1984/api/ws?src={name}
```
- Params: JSON text frames {"type":…,"value":…}: send {"type":"webrtc/offer","value":"<sdp>"} -> receive {"type":"webrtc/answer","value":"<sdp>"} then {"type":"webrtc/candidate","value":"candidate:…"} (send yours the same way); send {"type":"mse","value":"avc1.640029,avc1.64002A,avc1.640033,hvc1.1.6.L153.B0,mp4a.40.2,mp4a.40.5,flac,opus"} -> receive {"type":"mse","value":"video/mp4; codecs=\"avc1.64001F,mp4a.40.2\""} then binary fMP4 frames for MediaSource; send {"type":"hls","value":"<codecs>"} -> playlist text (rewrite to http://host:1984/api/hls/playlist.m3u8?id=…); send {"type":"mp4","value":"<codecs>"}; send {"type":"mjpeg"} -> binary JPEG frames; errors arrive as {"type":"error","value":"…"}. v2 form: {"type":"webrtc","value":{"type":"offer","sdp":…,"ice_servers":[…]}}
- Auth: Basic; Origin must match host (port ignored) unless api.origin: "*"
- Response: 101 Switching Protocols
- Notes: The hub's reverse proxy must forward WebSocket upgrades on /api/ws. ?dst= makes the socket a producer.
- Source: https://github.com/AlexxIT/go2rtc/blob/master/internal/api/ws/README.md

### Web Push: hub sends notification (web-push npm)

## Limits and caveats

- go2rtc's JPEG/MJPEG outputs (/api/frame.jpeg, /api/stream.mjpeg) only work if the stream already contains an MJPEG codec; for typical H.264/H.265 cameras you must either add a camera snapshot URL as a second source, or add 'ffmpeg:{name}#video=mjpeg' which requires an ffmpeg binary (not bundled with the go2rtc binary; bundled only in Docker/HA add-on). /api/frame.mp4 works without ffmpeg for H.264/H.265 snapshots.
- go2rtc has only HTTP Basic auth, skips auth entirely for localhost (unless local_auth: true), and CORS supports only origin '*'. Bind it to 127.0.0.1:1984 and reverse-proxy /api/ws (WebSocket upgrade), /api/webrtc, /api/frame.jpeg, /api/stream.* through the hub's authenticated HTTPS server; never expose :1984 directly. Restrict with api.allow_paths and exec.allow_paths because exec:/echo: sources can run arbitrary commands.
- WebRTC media bypasses the HTTP proxy: it needs port 8555 TCP/UDP reachable from the phone (LAN fine). When the phone is on 4G and the hub is behind CGNAT/router, WebRTC will often fail unless 8555 is forwarded or a TURN server is configured; video-rtc.js then falls back to MSE (fMP4 over the same WebSocket, which does traverse the proxy) and, on iOS Safari (no MediaSource; ManagedMediaSource only Safari 17+), to HLS. Design the remote path around MSE/HLS through the hub's tunnel, not WebRTC.
- Safari cannot autoplay WebRTC (go2rtc known problem); require a tap to start playback on iPhone.
- Web Push and service workers need a secure context: a real HTTPS origin with a certificate the phone trusts (self-signed LAN certs will block SW registration on iOS and make Android Chrome refuse push). Plan a domain + valid certificate (or a tunnel) for the hub even for LAN use.
- iOS: push works only in iOS/iPadOS 16.4+, only after the PWA is added to the Home Screen from a manifest with display standalone/fullscreen, permission must be requested from a user tap, every push must show a notification or Safari revokes the subscription, VAPID is mandatory, subject must not be mailto:…@localhost (403 BadJwtToken), payload <= 4 KB, and the hub must reach https://*.push.apple.com.
- Android Chrome: FCM endpoints (fcm.googleapis.com) must be reachable from the hub (fine over the SIM/4G path); Chrome shows 'This site has been updated in the background.' if the push handler does not show a notification; delivery works with Chrome closed but is subject to OS battery optimisations. Push carries only a small JSON payload, never video; the notification's click URL should deep-link into the camera/device page.
- Push subscriptions expire or are revoked: handle 404/410 from sendNotification by deleting the stored subscription and re-subscribe on app open (pushManager.getSubscription / subscribe again with the same VAPID key). Changing the VAPID key pair invalidates all existing subscriptions.
- Browser-direct MJPEG/snapshot fallback: cameras use HTTP Digest auth, which <img> tags cannot supply and which would expose credentials in the page; proxy camera JPEG/MJPEG through the hub. Chrome renders multipart/x-mixed-replace only for images (fine for <img>), and go2rtc notes native MJPEG in Chrome has a long-standing bug, preferring MJPEG over WebSocket. Hikvision MJPEG-over-HTTP requires the sub-stream to be re-encoded as MJPEG (losing the H.264 sub-stream); Dahua breaks snapshot.cgi if the RTSP sub-stream is MJPEG.
- Hikvision httpPreview/PTZ and Dahua CGI details come from Hikvision's how-to (via a secondary page) and from open-source integrations (hikvision-client, rroller/dahua), not from vendor SDK PDFs fetched here; treat exact PTZ argument values as medium confidence and verify against the owner's actual camera models.
- FFmpeg licensing: the convenient static builds are GPLv3 (gyan.dev, johnvansickle) or GPL/LGPL selectable (BtbN). Shipping an ffmpeg binary inside your installer brings GPL/LGPL obligations for ffmpeg itself (offer source/attribution); go2rtc and the hub only spawn it as a separate process. The LGPL BtbN variant lacks libx264/libx265, so H.264 encoding (e.g. go2rtc '#video=h264' transcodes) needs the GPL build, while MJPEG output and H.264 decoding do not (medium confidence, not legal advice). Simplest: let the user download ffmpeg separately or fetch it at install time and document the licence.
- Version drift: go2rtc v1.9.14 (2026-01-19), web-push 3.6.7, vite-plugin-pwa 1.3.0 (workbox 7.4.x) were current at research time (2026-09-30); pin versions and re-check release notes before implementing, since go2rtc's WebSocket protocol and video-rtc.js (v1.6.0) evolve together.
- go2rtc's own API doc lists /api/webrtc?src= in OpenAPI as POST; an older README summary claiming GET is wrong. Use POST with application/sdp for WHEP or the WebSocket flow.
